# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**WarRoomLive** — a low-latency, multi-user cross-department collaboration room. Real-time traffic is split across three planes: **WebRTC** for audio/video media, **WebSocket** for signaling and business events, and **Yjs CRDT** for collaborative shared notes. It is a monorepo with a React (TypeScript) frontend, a Java Spring Boot backend, and a Node collab service.

## Layout

- `backend/` — Spring Boot 3.3 signaling server (Java 21, Maven).
- `frontend/` — React 18 + TypeScript, built with Vite.
- `collab/` — Node 20 Hocuspocus (Yjs) document-sync service on `:1234`; persists an update log + compacted snapshots to Postgres when reachable, else memory-only. Enforces message-size/doc-size/rate limits; requires JWTs when `OIDC_ISSUER` is set. **Keep `@hocuspocus/server`, `extension-database` and `extension-redis` on one major version.** A newer `extension-redis` installs its own nested `@hocuspocus/server`, and the two versions then share document objects across the Redis channel: the nested code calls a callback the outer version's documents do not have, and the replica dies of an uncaught TypeError the first time awareness crosses instances. `tests/e2e/run.sh scale` covers this.
- `devidp/` — DEV-ONLY OIDC provider (fixed users alice/bob, in-memory key) used by the `docker-compose.oidc.yml` overlay; production swaps it for Keycloak/Entra via the `OIDC_*` env vars. Never deploy it publicly.
- `docs/architecture/roadmap.md` — phased plan mapping the target production tech stack onto this codebase; consult it before starting a new architectural increment.
- `README.md` — architecture diagram and run instructions (keep in sync with this file).
- `frontend/src/**/*.test.ts(x)` — vitest, the only frontend tests CI runs (`npm test`). `vitest.setup.ts` registers Testing Library's `cleanup`: this project runs vitest **without globals**, so it is not automatic, and without it every render stays in the document and `screen` queries see components from finished tests. Cover what is pure and policy-heavy: the reconnect close-code rules, the quality thresholds/hysteresis, host-only affordances. Anything needing a browser or a stack belongs in `tests/ui/` or `tests/e2e/`.

For questions only a browser answers: audio is *audible* (measure with `captureStream()`, never `createMediaElementSource` — it returns silence for srcObject streams either way), editors are wired to their documents, controls are offered to the right person. Not in CI.

Shared harness in `lib.mjs`; suites: signaling, room-acl, crdt, capacity, reconnect, limits, retention, agenda, recordings, attachments, oidc, token-lifecycle, events, crdt-hardening, scale. Not run in CI.

Not run in CI. `docker-compose.backup-s3.yml` stacks on it: an rclone shipper syncs the backups volume into MinIO through a `crypt` remote (client-side encrypted contents *and* names), and `tests/dr/restore-s3-drill.sh` restores from the bucket alone. Backups destined for object storage must use tar format (`tests/dr/backup.sh tar`) — a plain backup's empty directories (`pg_notify`, `pg_subtrans`, …) do not survive a round trip through object storage and the restored cluster refuses to start.

CI does not build images — verify Docker changes by running the stack.

- `docker-compose.scale.yml` — opt-in horizontal scaling: Redis + backend×2 (`redis` profile) + collab×2 (`extension-redis`); nginx round-robins via request-time DNS. Verify with the stack, not unit tests.

Backend adds the `redisha` profile (`application-redisha.yml` → `spring.data.redis.sentinel.*`); collab switches ioredis to Sentinel via `REDIS_SENTINEL_NODES`/`REDIS_SENTINEL_MASTER`. Failover drill: `tests/ha/failover-drill.sh` (kills the master, asserts promotion + signaling/CRDT recovery). Startup constraint: the backplane's first Redis command runs in `RedisBackplane`'s `SmartLifecycle.start()`, never during bean construction — Lettuce records command latency on its event loop and the Prometheus exemplar tracer lookup needs the bean-factory lock the constructing thread would hold (deadlock).
- `docker-compose.turn.yml` — opt-in coturn relay for mesh calls behind strict NATs; backend advertises it via `iceServers` in `/api/media/config` (env `TURN_URLS`/`TURN_USERNAME`/`TURN_PASSWORD`, all three required).
- `docker-compose.recording.yml` (stacks on the sfu overlay) + `infrastructure/livekit/livekit-recording.yaml`/`egress.yaml` — opt-in meeting recording: LiveKit Egress (room composite, needs Redis + 2gb shm) uploads MP4s to MinIO; backend drives it via twirp (`RecordingController`, dev creds in the overlay) and receives LiveKit webhooks at `/api/livekit/webhook` (self-authenticating body-hash JWT — keep it on the security permit list). With the events overlay, completion becomes `meeting.recording.completed`. The webhook also writes a `recordings` row (V6, postgres profile) in the same transaction as the event, so the in-app library and the backbone cannot disagree; redelivery is idempotent on the egress id. **Playback is a presigned GET, never a proxied stream or a stored URL**: only the object key is persisted, `RecordingLibraryController` mints a short-lived SigV4 URL per request (`S3Presigner`, hand-rolled — no AWS SDK), and nginx's `/recordings/` location strips the prefix and rewrites `Host` to the object store so the request that arrives is byte-for-byte the one that was signed. `proxy_pass` with a variable does not apply nginx's URI-replacement rule, hence the explicit `rewrite`.
- **Meeting domain** (`meetings/`, postgres profile): `Backplane.tryRegister`/`unregister` return cluster member counts; the 0→1 join opens a `meetings` row (+`meeting.started`), the →0 leave closes it (+`meeting.ended` with duration/peak), and room-full rejections emit `participant.rejected`. Rows and events commit in one transaction.
- `docker-compose.events.yml` — opt-in event backbone: backend profiles `postgres,kafka`, Redpanda broker. Business events commit transactionally into `outbox_events` (`events/` package, `OutboxRecorder` inside the aggregate's transaction; the collab service inserts into the same table inside its snapshot transaction when `EVENTS_ENABLED`) and `OutboxPublisher` ships them at-least-once to topic `warroom.events` — consumers dedupe on `eventId`. The `kafka` profile requires `postgres`. To emit a new event type: record it inside the owning transaction, bump `schemaVersion` on shape changes. Current types: `chat.message.created`, `participant.joined`, `participant.left`, `participant.rejected`, `participant.kicked`, `document.snapshot.created`, `meeting.started`, `meeting.ended`, `meeting.recording.completed`, `meeting.recording.deleted`, `attachment.created`, `attachment.deleted`, `todo.created`, `todo.updated`, `todo.completed`, `todo.reopened`, `todo.deleted`, `calendar.event.created`, `calendar.event.updated`, `calendar.event.deleted`, `room.locked`, `room.unlocked`.
  With the events overlay the envelope contract also lives in Redpanda's built-in schema registry (`:8081`, subject `warroom.events-value`): the indexer registers the bundled schema at startup and then validates against whatever the registry serves as latest, falling back to the bundled copy when `SCHEMA_REGISTRY_URL` is unset or unreachable.
- `indexer/` — Node 20 example consumer: builds `audit_log` + `message_search` (V4 migration; served by `GET /api/search/messages`). Consumption is idempotent (event_id PK, both projections in one transaction, offsets committed after write); poison messages are counted and skipped, DB errors retry. Metrics on `:9400/metrics`.
- `docker-compose.prod.yml` + `infrastructure/edge/` + `docs/runbooks/deployment.md` — deploying onto a host whose `:80`/`:443` **already belong to another site's reverse proxy** (the `live.tommy-huang.dev` case). Publishes the frontend on **loopback only** and brings no edge of its own — `docker-compose.tls.yml` is the wrong overlay there, it binds `:80`/`:443` and collides. Refuses to start without `DB_PASSWORD`/`PUBLIC_ORIGIN` rather than deploying with the repo's development defaults. **The extra proxy hop breaks the REST rate limiter unless corrected**: the backend keys on the *last* `X-Forwarded-For` entry (the only one a client cannot forge in the single-proxy topology), which behind an edge becomes the edge's address for everyone — one bucket for the whole internet. `infrastructure/edge/real-ip.conf`, mounted only by this overlay, makes the frontend nginx resolve `$remote_addr` to the real client so the entry it appends is the browser again. Media never goes through the edge (SRTP/UDP): mesh needs no extra ports, TURN and the SFU need their own, published directly. `tests/deploy/verify.sh` is the post-deploy check — it targets the two failures this topology hides (a WebSocket that never upgrades, and a rate limiter that has collapsed every client into one bucket), and adds loopback-only checks when run on the server.
- `docker-compose.tls.yml` + `Caddyfile` — opt-in TLS overlay (WarRoomLive owns the host). Adds a Caddy edge that terminates TLS (automatic Let's Encrypt via `SITE_ADDRESS`, or its internal CA for `localhost`) and reverse-proxies to the frontend; the overlay clears the frontend's published ports with `!override []`. Apply with `-f docker-compose.yml -f docker-compose.tls.yml`. The base compose stays plaintext for simple local runs.

## Commands

Backend (`cd backend`):
- `mvn spring-boot:run` — run the server on `:8080`.
- `mvn test` — run all tests.
- `mvn -Dtest=SignalingHandlerIntegrationTest test` — run a single test class (append `#methodName` for one method).
- `mvn package` — build an executable jar into `target/`.

Frontend (`cd frontend`):
- `npm install` — install dependencies (first run).
- `npm run dev` — Vite dev server on `:5173`; proxies `/api` and `/ws` to the backend on `:8080`, and `/ws/doc` to the collab service on `:1234`.
- `npm run build` — type-check (`tsc`) then production build into `dist/`.
- `npm run typecheck` — type-check only.

Collab service (`cd collab`):
- `npm install` — install dependencies (first run).
- `npm start` — run Hocuspocus on `ws://localhost:1234`. Persists to Postgres if reachable (env: `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASSWORD`), otherwise runs memory-only. Optional for local dev — everything except shared notes works without it.

Local end-to-end: run the backend and `npm run dev` together, then open two browser tabs on `localhost:5173` and join the same room. `getUserMedia` only works on `localhost` or HTTPS.

## Architecture

The signaling server **never touches media** — it only relays SDP offers/answers and ICE candidates to the addressed peer, and broadcasts room membership changes. Media (SRTP) flows peer-to-peer.

- **Media transport is mode-switched, decided by the backend**: `GET /api/media/config` returns `mesh` (default) or `sfu` (when `LIVEKIT_URL`/`LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET` are set — see `docker-compose.sfu.yml`). The frontend picks `WebRtcRoom` (full mesh) or `SfuRoom` (LiveKit) accordingly; both implement the `MediaRoom` interface, and everything else (signaling, chat, notes) is transport-agnostic. Mesh is simplest/lowest-latency for ~6–8 people; the hard per-room cap (`warroomlive.signaling.max-room-size`, default 8, raised to 50 in the SFU overlay) and the frontend warning at `ROOM_WARN_THRESHOLD` (6, mesh-only) protect it. LiveKit participant identity == signaling `selfId`, which is what maps SFU tracks onto the peer-keyed UI state — preserve that invariant. LiveKit tokens are signed server-side in `MediaController` (room-scoped video grant); the API secret never reaches the browser.
- **Glare avoidance**: the peer already in the room initiates the offer to a newcomer (driven by the server's `peers` vs `peer-joined` messages). Preserve this asymmetry when changing negotiation.
- **Link quality is measured per peer, and acted on per peer**: `webrtc/quality.ts` keeps the judgement (thresholds, degrade/restore hysteresis, windowed loss from cumulative counters) as pure functions so it is unit-testable; only `sampleConnection` touches `getStats()`. Sustained poor quality caps *that* sender's video (`setParameters`), never everyone's; restoring is deliberately slower than degrading so a flapping link does not thrash resolution. A `failed` connection triggers an ICE restart from the lower peer id only — both sides restarting would collide. SFU mode maps LiveKit's `ConnectionQualityChanged` onto the same shape and applies no degradation of its own (adaptiveStream/dynacast already do that).
- **Signaling reconnects; the app re-joins**: `SignalingClient` retries a dropped socket with capped backoff + jitter, rebuilding the URL per attempt so a renewed token is picked up. It never retries after a kick (4403) or a deliberate `close()` — retrying would re-enter a room the server just ejected us from. Transport recovery is all it does: `onReconnected` fires only on a *recovery* (never the first connect) and the app re-joins, replays its media/hand flags, and rebuilds mesh peer connections (`MediaRoom.handleReconnect`; a no-op for SFU, whose media rides LiveKit's own connection). `peers` **replaces** the membership map rather than merging, or peers who left during the outage linger. Server side, `RoomManager.remove` ignores a close whose session the peer already replaced — otherwise a late close (laptop sleep) evicts the reconnected peer. Covered by `ReconnectIntegrationTest` and `tests/e2e/run.sh reconnect`.
- **Signaling envelope is shared contract**: `SignalMessage` exists on both sides — `backend/src/main/java/com/warroomlive/signaling/SignalMessage.java` and `frontend/src/signaling/types.ts`. Adding or renaming a message `type` requires updating **both**, plus the `switch` in `SignalingHandler` and the handlers in `WebRtcRoom`.
- **All three planes carry abuse limits, and they mirror each other**: signaling has a per-connection token bucket (`limits/RateLimiter`, sustained rate with a 2× burst so a join plus a flurry of ICE candidates is never throttled), a container-level frame cap, and a chat length cap checked before the message reaches durable storage; collab has message-rate, update-size and doc-size limits; the HTTP API uses the same bucket per caller (`limits/RestRateLimitFilter`, `warroomlive.api.max-requests-per-second`). The responses differ by intent: signaling rate excess is **dropped** (a burst is usually a bug or a bad network, and closing would take chat, presence and negotiation down with it), an over-long chat is **refused with an error** (never truncated — the sender must know it did not send), an oversized frame is refused by the container, which closes with 1009, and HTTP excess gets **429 + Retry-After** (an HTTP caller is waiting for an answer and can back off if told to). Rejections are counted under `warroomlive.signaling.messages.in` and `warroomlive.api.rejected`.
  The REST filter runs **ahead of authentication** so a flood is refused before it costs a signature verification or a JWKS fetch, which is also why it keys on address, not subject. That address is the **last** `X-Forwarded-For` entry — nginx appends the peer it saw, so earlier entries are client-supplied and forgeable; reading the first would let any caller mint a fresh allowance per request. Health, `/api/auth/config` and the self-authenticating LiveKit webhook are exempt. HTTP has no disconnect to release a bucket on, so idle ones are swept periodically.
- **List endpoints are pages, not tables**: `GET /api/recordings/{room}` and `GET /api/search/messages` take `limit`/`offset`, clamped by `web/Pages` (default 50, max 200; nonsense falls back rather than erroring — a negative OFFSET is a Postgres error). Any new collection endpoint should do the same.
- **Room ACL is host-centric and server-enforced**: the peer that opens a room is its host (handed to the longest-present member on leave — arbitrary member on Redis); only the host may `lock`/`unlock` (newcomers bounce with `room-locked`; `tryRegister` returns `REGISTER_LOCKED`) and `kick` (target gets `kicked` then close 4403; cross-node kicks ride the backplane's `toPeer` delivery, which closes on the hosting node). Host/locked live in the backplane (`RoomState`; Redis: `warroom:roommeta:<room>`, assigned/handed over inside the register/unregister Lua scripts). Privileged senders are authenticated against the connection's own join identity (`RoomManager.locationOf`) — never trust `from` alone. `room-state` `{host, locked}` goes to each joiner and is re-broadcast on every change.
- **Room membership is backplane-abstracted**: `RoomManager` always tracks this node's local sessions; the `Backplane` interface answers cluster-wide questions. Default = `LocalBackplane` (single process, publishing no-ops). The `redis` profile swaps in `RedisBackplane`: membership directory in Redis hashes (entries carry the hosting node id), cross-node relay/broadcast over pub/sub channel `warroom:signal`, node heartbeats with lazy ghost pruning. When touching `SignalingHandler`, keep the pattern: deliver to local sessions via `RoomManager`, then `backplane.publish*` for other nodes — never double-deliver. The room-capacity decision belongs to `Backplane.tryRegister` and is atomic in both impls (per-room `compute` locally, a Lua script on Redis) — don't reintroduce read-then-register checks in the handler.
- **Chat persistence is behind `ChatRepository`** (`chat/` package) with two profile-selected implementations: `InMemoryChatRepository` (default, `@Profile("!postgres")`, bounded ring buffer) and `JpaChatRepository` (`@Profile("postgres")`, Postgres). Because `spring-boot-starter-data-jpa` is always on the classpath, the default profile **excludes** the JPA/DataSource auto-configs in `application.yml`; `application-postgres.yml` clears that exclusion. If you add a second JPA repository, both profiles must still start — keep the exclusion list in sync. On join the server replays recent chat as a `history` message.
- **Nothing durable is kept by default forever, but nothing is deleted by default either**: `retention/RetentionService` (postgres profile, hourly) sweeps recordings + their objects, chat + its `message_search` projection, `audit_log`, and *published* `outbox_events`. **Every period defaults to 0 = keep forever** — a retention job that deleted on deploy would be a terrible surprise, so an operator opts in per data type via `warroomlive.retention.*-days`. Deletions happen in bounded batches (500 rows, 20 batches per table per pass), each its own transaction via `TransactionTemplate` — `@Transactional` on a method the same bean calls does nothing. Chat and its search projection share one period deliberately: deleting the message but keeping the index leaves search returning text that exists nowhere else. Unpublished outbox rows are never touched — they are the queue, not history. A recording is deleted **object first, then row**, so a failed object delete leaves the row for the next pass rather than orphaning a file; the shared path is `RecordingStore.delete(recording, reason, actor)`, also used by `DELETE /api/recordings/{room}/{id}`, and both emit `meeting.recording.deleted`. That endpoint carries only the API's ordinary protection (nothing by default, authenticated under `oidc`) — there is no binding between a REST identity and a signaling peer id, so it is **not** host-gated; what it does provide is attribution via the event's `actor`.
- **Schema is Flyway-owned** (`backend/src/main/resources/db/migration/`, postgres profile): Hibernate runs `ddl-auto: validate`, so entity changes need a matching `V<n>__*.sql` migration. The collab service's tables live in the same migration chain (V2); its own `CREATE TABLE IF NOT EXISTS` statements are only a fallback for running without the backend — keep both in sync. Existing databases baseline at version 0 (`baseline-on-migrate`).
- WebSocket allowed origins are configured via `warroomlive.signaling.allowed-origins` in `application.yml` (`*` for local dev; lock down per environment).
- **Shared notes and the whiteboard are one CRDT plane**: `CollabPanel` (frontend) owns a single Yjs session per room (`useCollabSession`) with two surfaces as tabs — `NotesEditor` (TipTap) and `BoardCanvas` (Konva; durable strokes/stickies in the `board:*` shared types, in-progress strokes and cursors on awareness only). Everything syncs through the `collab/` Hocuspocus service at `/ws/doc` — never through the signaling socket. One Yjs document per room, named `warroom:<room>`. Durable state is two-tier in Postgres: every update appends to `collab_update` (crash safety), the debounced snapshot lands in `collab_document` and trims covered log rows (compaction) — keep fetch/store symmetric if you touch either. Ephemeral state (cursors, awareness) is relayed only, throttled client-side to ~25 Hz. The signaling `SignalMessage` contract is not involved; don't add note-related message types to it.
- **Identity is the server's, not the client's**: the WS handshake captures the JWT's subject and vouched-for name (`WebSocketConfig.SUBJECT_ATTRIBUTE` / `VERIFIED_NAME_ATTRIBUTE`); on `join` the verified name **overrides** whatever the client sent, and the subject rides into the backplane directory (`tryRegister(..., subject, ...)`, `Backplane.subjectOf`). Without OIDC there is no subject and the client's name is all there is — the zero-dependency default. Subjects stay **out of `PeerInfo`**: the room needs names, not everyone's account identifier. This is what lets an authorization decision be made from outside the connection, e.g. `DELETE /api/recordings/{room}/{id}` and `/api/attachments/...` are **host-gated when the room's host has a known subject**, and fall back to attribution-only when it does not (empty room, or no IdP).
- **Files shared into a room** (`attachments/` + `web/AttachmentController`, postgres profile + the recording overlay's object store): upload is presign → browser PUTs straight to the store → confirm, and the **row is written last** (a row without an object is a broken download; an object without a row is invisible and retention sweeps it). The object key is server-chosen and prefixed `attachments/<room>/`, checked on confirm so a key cannot be claimed into another room. The size limit is enforced **twice** — declared size before signing, stored size (`ObjectStore.sizeOf`) at confirm, since a presigned PUT cannot enforce one itself. `ObjectStore` is now the single place that knows the store's address and signs for it (`presign`/`sizeOf`/`delete`); nginx serves both `/recordings/` and `/objects/` with the same Host rewrite, the latter also allowing PUT bodies. A completed upload is announced to the room via `SignalingHandler.broadcastToRoom` as an `attachment` message.
- **A room's to-do list and calendar are database rows, not CRDT** (`agenda/` + `web/TodoController`/`CalendarController`, postgres profile, V9): they are durable business records — owner, due date, completion — that people query ("what is still open"), audit ("who closed it") and that outlive the meeting, so they follow the "durable → Postgres" rule rather than joining the notes and whiteboard in the Yjs document. A CRDT cannot be queried, validated, or fed into the event backbone. **Ordering is the server's** (open first, soonest-due first, undated last; the calendar reads forwards from `from`, default now) — a client that re-sorts is how two people end up discussing different "first" items. Completion is stored as a time + author, and re-completing is a no-op so a second click cannot rewrite who finished it; only a real transition emits an event. Adding and completing are open to anyone in the room (a list only the host may tick off is not shared); **deleting is host-gated** via `web/RoomAuthorization`, which also owns the `caller()` / `requireHostIfKnown` pair the recording and attachment controllers use — call it **before** the lookup, or a 404 leaks existence. Changes broadcast `agenda` with `{kind}` so only the affected list refetches.
- **The agenda is captured as one line, parsed client-side** (`frontend/src/agenda/capture.ts`): `寄簡報 @bob 明天15:00` yields `{text, assignee, dueAt}`. The parser's one invariant is that **anything it does not recognise stays in the text** — including values it recognised but rejected (`25:00`, `2/31`), which are put back rather than dropped. It handles 今天/明天/後天, 週X/禮拜X/星期X and English weekdays, `HH:MM`/`HH點`, `M/D` (a past date rolls to next year), `N天後`/`N小時後`; a date with no time means 23:59 local, a bare time already past means tomorrow. `\b` is ASCII-only so it never matches after a CJK character — the time pattern uses explicit lookarounds instead. The panels parse on every keystroke via one `useMemo` shared by the preview and the submit, so what "解讀為" shows cannot disagree with what is sent. The server still validates everything; this is a typing convenience, not a trust boundary.
- **One sidebar panel is open at a time, at every width** (`.sidebar[data-active]` in `App.css`, `sidebarTab` in `App.tsx`): seven panels stacked in a 320px rail give each a sliver. `sidebarPanels` is derived from what is actually rendered, so a tab never switches to a blank sidebar. Both panels stay in the DOM and CSS hides the inactive one — any test selector for a row must be scoped to `[data-panel="…"]` or it will count the calendar's rows as the to-do list's.
- **Day/night skins are one token set, chosen by the local clock** (`frontend/src/theme/`, `frontend/src/theme.css`): `resolveTheme(preference, now, prefersDark)` is pure and unit-tested; `useTheme` applies `data-theme` + `color-scheme` to `<html>` and re-resolves on a timer aimed at the next boundary (07:00/19:00), on `matchMedia` change, and on `visibilitychange` (a laptop asleep through dusk never fires the timer). OS preference is handled **asymmetrically on purpose**: `dark` overrides the clock (it is opt-in, often accessibility), `light` defers to it (it is what browsers report when nothing is set). Every colour in `App.css` must be a `var(--…)` token or the two skins drift apart one rule at a time — `--tile-bg`/`--on-tile` are deliberately identical in both, because video is video and a name badge on its own black scrim must not follow the page's ink. `--skin-fade` is defined as `none` **before** the `prefers-reduced-motion: no-preference` query that turns it on; the other order leaves the crossfade silently dead on a specificity tie.
- **Auth is profile-gated and server-side**: default = permit-all (`SecurityConfig`, `!oidc` chain); the `oidc` profile turns the backend into an OAuth2 resource server (JWT via header or `access_token` query param for WS handshakes) and collab verifies the same JWTs in `onAuthenticate` when `OIDC_ISSUER` is set. `issuer` (public string browsers see, must equal the JWT `iss`) and `jwk-set-uri` (internal fetch address) are deliberately separate because of the single-origin proxy. The frontend adapts via `GET /api/auth/config` + `AuthGate` (PKCE, `oidc-client-ts`) — never enforce anything client-side only.
